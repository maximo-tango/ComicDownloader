# Image Hunter v1.1.0 테스트 결과

- 실행일: 2026-10-29
- 환경: Linux(Codespace, CPU 2개), Node.js 24.21.0, Chrome for Testing 148.0.7778.97 (headless, Puppeteer 24)
- 결과: **단위·브라우저 테스트 75/75 통과**, **종단 간(E2E) 25/25 단계 통과**
- 실행하지 않은 항목은 맨 아래 "실행하지 않은 테스트"에 따로 적었습니다. 실행하지 않은 항목을 통과로 적지 않았습니다.

```bash
npm test            # 단위 67건 + 브라우저(실제 Chrome 페이지에서 수집기 실행) 8건
npm run test:e2e    # 확장 프로그램 전체를 Chrome에 로드해 25단계 실행
```

> E2E 조건: Puppeteer는 툴바 버튼을 누를 수 없어서 activeTab 권한 부여를 재현할 수 없습니다. 그래서 테스트용 사본의 manifest에 `http://127.0.0.1/*`만 추가했습니다(그 페이지에서 메뉴를 열었을 때와 같은 접근 범위). 두 번째 출처 `http://localhost`는 권한 없이 두고, 권한이 없을 때의 동작을 확인했습니다. 실제 activeTab 흐름은 수동 테스트 M2입니다.

## 테스트 중 발견해 고친 문제

| # | 문제 | 원인 | 수정 | 회귀 테스트 |
| --- | --- | --- | --- | --- |
| 1 | 여러 다운로드를 한꺼번에 시작할 때 가끔(약 10회에 1번) 다운로드 화면이 응답하지 않음 | Chrome이 서비스 워커를 교체했는데, 대기열 저장이 250ms씩 미뤄져 있어 새 워커가 빈 상태로 시작함. 화면 요청은 답을 받지 못한 채 기다림 | 대기열을 작업 추가 직후와 다운로드 시작 직전에 바로 저장. 재시작한 워커는 이미 시작된 다운로드를 URL로 찾아 연결. 화면 요청은 8초 안에 답이 없으면 한 번 다시 보냄(요청 ID로 중복 처리 방지) | E2E [19], [28]. 재현 스크립트 반복 실행에서 상태 손실 없음 |
| 2 | 탭이 다른 페이지로 이동한 뒤 재검색하면 목록이 비고 결과 안내도 없음 | 목록을 새로 만들면서 검색 세대 번호가 바뀌어, 진행 중이던 검색이 자기 결과를 버림 | 새 페이지로 바꾼 뒤 검색 세대를 이어받도록 수정 | E2E [27] |
| 3 | `Access-Control-Allow-Origin: *`를 쓰는 CDN 이미지의 크기를 확인하지 못하고 PDF에서도 빠짐 | 쿠키를 포함한 요청은 와일드카드 CORS에서 거부됨 | 권한이 있는 출처에만 쿠키를 보내고, 나머지는 쿠키 없이 요청 | 단위, E2E "URL 목록의 PDF" |
| 4 | 결과 CSV/JSON이 `.txt`로 저장됨 | data URL의 MIME이 항상 `text/plain`이라 Chrome이 확장자를 바꿈 | 확장자에 맞는 MIME(`text/csv`, `application/json`) 사용 | E2E [24] |
| 5 | 실패한 항목을 다시 선택해 다운로드하면 같은 URL 작업이 2개 생기고, 이후 "실패 항목 재시도"에서 두 번 받게 됨 | 다운로드 버튼이 실패한 작업 대신 새 작업을 만듦 | 실패·취소 상태의 기존 작업을 다시 시도하도록 변경(URL 직접 입력도 같음) | E2E [21] |
| 6 | 서비스 워커가 재시작되면 다운로드 화면의 진행률 갱신이 멈춤 | 화면의 연결(port)이 끊긴 뒤 다시 연결하지 않음 | 연결이 끊기면 자동으로 다시 연결 | E2E [28] |
| 7 | 서버가 206으로 답하면서 `Content-Range`를 숨기면(CORS) 부분 길이(128KB)를 전체 파일 크기로 표시 | 206 응답에서 `Content-Length`를 사용 | 206에서는 `Content-Range`만 사용하고, 없으면 "확인 불가" | 단위 |
| 8 | 핫링크 방지 이미지가 페이지에서 읽은 크기 때문에 "원본 후보 확인"으로 보임 | 확장 프로그램이 그 URL에 접근하지 못하는 경우를 상태에 반영하지 않음 | 선택한 URL에 접근할 수 없으면 "확인 불가"(크기는 페이지에서 읽은 실제값 유지) | 단위, E2E [9][10] |
| 9 | `onDeterminingFilename` 사용 | 이 리스너가 있으면 Chrome이 사용자의 모든 다운로드마다 확장 프로그램을 깨워 기다림 | 파일명을 다운로드 시작 전에 정하고 리스너 제거. 서버 파일명은 원본 확인 단계에서 `Content-Disposition`으로 읽음 | E2E [19](`server-named.png`) |

1번은 원인을 끝까지 특정하지는 못했습니다. 어떤 조건에서 Chrome이 워커를 교체하는지는 headless 환경에서 재현이 들쭉날쭉했고, 로그를 켜면 재현되지 않았습니다. 그래서 워커가 언제 교체되어도 상태를 잃지 않도록 고쳤습니다. 수정 후 E2E 전체와 재현 스크립트 반복 실행에서 상태 손실이나 응답 없음은 다시 나타나지 않았습니다.

## 실행하지 않은 테스트 (수동 확인 필요)

아래 항목은 자동화하지 않았고 **실행하지 않았습니다**. 절차는 [tests/README.md](../tests/README.md)의 M1–M12에 있습니다.

- 실제 툴바 버튼과 activeTab 권한 흐름 (M2), 접근할 수 없는 페이지에서 연 메뉴 (M3), 권한이 사라진 뒤 재검색 (M4)
- 선택 권한 허용 창 (M5): headless에서는 권한 창을 누를 수 없음
- **Windows 11 실기**: 한글·금지 문자가 들어간 폴더 저장(M6), 저장 위치 확인 창이 켜진 Chrome(M8)
- `chrome://serviceworker-internals`로 워커 중지 (M9): 자동 테스트에서는 CDP로 같은 동작을 실행함
- 실제 무한 스크롤 사이트, 대형 웹툰 PDF (M10, M11), 다크 모드 화면 (M12)
- 로그인이 필요한 실제 사이트, 수십 MB 이미지의 메모리 사용량
